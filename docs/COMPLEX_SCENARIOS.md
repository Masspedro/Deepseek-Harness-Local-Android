# 复杂场景支持设计：从文本界面到游戏

> 技术沉澱 · 2026-10-10 · 本文是设计文档（未全部实现），Games 部分涉合规风险，
> 实现前须主人确认（见「合规红线」）。

## 1. 场景分级：先搞清楚"难在哪"

| 级别 | 场景 | 感知源 | 难度 |
|---|---|---|---|
| **L1 标准 UI** | 设置、社交、电商、系统应用 | 无障碍节点树（**已有**） | 低 |
| **L2 半自定义** | WebView/Flutter/RN、混合页面 | 节点树 + 帧差兜底 | 中 |
| **L3 纯 Canvas/游戏** | 手游、Canvas 游戏、视频 App | **无节点树**，必须看画面 | 高 |
| **L4 真实世界** | 摄像头、扫码、AR | 视觉多模态 | 高（超出 UI 自动化） |

**关键事实**：游戏（L3）用 Canvas/OpenGL 渲染，**无障碍节点树是空的**——
FastPicker 的输入直接没了。这不是"优化一下」能解决的，是**感知源的根本不同**。

## 2. 架构：三条路径，一套验证

```
                    ┌─────────────────────────────┐
                    │   决策层（谁来决定做什么）      │
                    │  D1 本地快路径（FastPicker）    │  ← 文本，<100ms
                    │  D2 云端多模态（视觉+文本）      │  ← 复杂/游戏，1-3s
                    │  D3 预录宏/用户                │
                    └──────────┬──────────────────┘
                               │ 统一「意图」格式
                    ┌──────────▼──────────────────┐
                    │   执行层（本地，不思考）        │
                    │  A1 无障碍手势（已有）          │
                    │  A2 动作原语库（连点/摇杆/滑动） │  ← 新增
                    └──────────┬──────────────────┘
                               │
                    ┌──────────▼──────────────────┐
                    │   验证层（做对了吗）            │
                    │  V1 事件流 changed（已有）      │
                    │  V2 帧差对比（新增，通用）      │
                    └─────────────────────────────┘
```

**三条路径不是三套系统**——执行层和验证层是**共享**的。这保证：
- 文本场景走 D1，游戏场景走 D2，但**执行和验证同一套代码**
- 加入新决策源（如更大的本地模型）不用重写其他层

## 3. L3（游戏）到底缺什么、怎么补

### 3.1 缺的三样

| 缺失 | 后果 | 补法 |
|---|---|---|
| **无节点树** | 不知道屏幕上有什么 | **实时帧**（MediaProjection）+ 云端视觉理解 |
| **无稳定文本** | 无法用嵌入匹配 | 靠**空间约定**：区域 + 相对位置 |
| **高频交互** | 每步 3s 云端往返太慢 | **动作原语**一次下发长序列 + **本地宏** |

### 3.2 感知：两条互补

**a) 帧差（本地，~10ms）** —— 只回答「画面变了没」
- `takeScreenshot()`（无障碍已有，API 30+）降采样到 64×64 灰度
- 与上一帧算像素差 → 得出「变化区域比例」和「变化位置」
- **用途**：验证点击是否生效、检测加载完成、检测弹窗出现、检测画面卡住

**b) 云端视觉（1-3s）** —— 回答「这是什么、该点哪」
- 把降采样截图（如 720p JPEG）发给有多模态能力的模型
- Prompt 约束输出格式：`{"tap":[x,y]}` / `{"swipe":[...]}` / `{"wait":true}` / `{"done":true}`
- **只在必要时调用**（帧差检测到画面变化后、或定时）

### 3.3 执行：动作原语库（游戏的核心）

游戏操作不是「点一下」，是这些**可复用原语**：

| 原语 | 参数 | 典型用途 |
|---|---|---|
| `tap` | x,y | 单次点击 |
| `repeat-tap` | x,y,count,intervalMs | 连点（刷材料/快速升级） |
| `long-press` | x,y,durationMs | 蓄力/复制 |
| `swipe` | 起止点+durationMs | 翻页/瞄准 |
| `drag` | 起点→终点，rel=true 相对位移 | 虚拟摇杆/拖拽 |
| `pinch/spread` | 中心+两指位移 | 缩放 |
| `joystick` | 摇杆中心,方向角,角度,时长 | 移动（相对位移，**不依赖绝对坐标**） |

**关键设计：原语全部用「相对 + 区域」而非绝对像素**——不同分辨率/不同 UI 缩放下都能复用。

### 3.4 一个游戏任务的完整流程示例

任务：「打开王者荣耀（举例）训练营，练习 5 分钟补刀」

```
1. 云端拆解为条件计划（1 次往返，2-3s）：
   [
     {"launch": "王者荣耀"},
     {"wait-screen-changed": true},                 // 等登录界面出现
     {"branch": [
        {"when-frame-unchanged-after": 3000, "do": [{"tap-region": "center"}, ...]},  // 防卡登录
        {"when-ocr-contains": "进入游戏", "do": [{"tap": "进入游戏位置"}]}
     ]},
     ...
   ]
2. 本地闭环执行：
   - 用帧差判断画面变化（10ms）
   - 用原语执行（连点/滑动）
   - 失败 → 帧差检测 → 本地重试一次
   - 两次失败 → 截屏 + 上下文升级云端（2-3s）→ 新计划
3. 全程只在「真歧义」时问云端
```

## 4. 关键机制细节

### 4.1 帧差（Framer）

```
capture() → 降采样(64×64 灰度) → 与 prev 比对 →
  { changedRatio: 0.0~1.0, hotRegions: [ {x,y,w,h,ratio} ] }
```
- **降采样后再算**：64×64=4096 像素，一次比对 <5ms；原图 1080p=230 万像素太慢
- 节流：验证模式 200ms 一张够；游戏实时模式用 MediaProjection ~500ms 一张
- **不存原图**（隐私+内存），只存降采样指纹

### 4.2 屏幕指纹（Screen Fingerprint）

- 帧差指纹 + 无障碍节点摘要（文本场景）合成唯一 key
- **用途**：
  - 「这屏我见过吗」→ 复用上次决策（**0ms，零云端调用**）
  - 分支判断（条件计划的 `when` 大量基于它）
  - 死循环检测（同一指纹出现 3 次 = 卡住了）

### 4.3 条件计划（Conditional Plan）

```json
{
  "goal": "…",
  "steps": [
    {"op": "launch", "arg": "pkg"},
    {"op": "wait-frame-changed", "timeoutMs": 8000},
    {"op": "branch", "cases": [
        {"when": "fingerprint-in", "keys": ["login"], "do": [...]},
        {"when": "ocr-contains", "text": "进入", "do": [...]},
        {"when": "always", "do": [{"op": "tap-region", "arg": "center"}]}
    ]},
    {"op": "primitive", "name": "repeat-tap", "x": 0.5, "y": 0.8, "count": 10, "intervalMs": 100},
    {"op": "verify-frame-changed", "else": "escalate"}
  ],
  "onEscalate": "cloud-with-screenshot"
}
```

执行器（本地，Kotlin）：解释 JSON → 调执行层 → 调验证层 → 分支 → 失败处理。

### 4.4 安全兜底（必须）

- **上限保护**：单次计划最多 N 步（默认 50）、总时长上限（默认 5 分钟）、
  单 App 每日宏执行次数上限 → 防死循环跑飞
- **用户接管检测**：`scr interference` 已有，执行中原用户触摸立即暂停
- **随时可停**：通知栏停止按钮 / 无障碍事件热键

## 5. 合规红线（重要，必须先确认）

**游戏自动化是双刃的**。本设计**只支持以下合规场景**：

| 允许 | 说明 |
|---|---|
| ✅ 自己的游戏/开源游戏测试 | 无争议 |
| ✅ 无障碍辅助 | 帮助运动障碍玩家完成重复操作 |
| ✅ 单机游戏挂机（用户自己的号） | 风险用户自担，须明确提示 |
| ✅ 应用自动化测试 | QA 场景 |

| **拒绝** | 原因 |
|---|---|
| ❌ **外挂/作弊工具** | 破坏游戏公平，涉违法 |
| ❌ **绕过反作弊** | 指纹隐藏、协议伪造等 |
| ❌ **代练/打金服务** | 违反几乎所有游戏 ToS，黑产 |
| ❌ **PVP 自动对战** | 破坏他人体验 |

**实现要求**：游戏自动化入口要有**一次性合规提示**（「仅限合规场景，违规使用后果自负」），
且**不做任何反检测/绕过**能力。

## 7. 建议实现顺序（按「风险 × 收益」排）

1. **帧差验证（Framer）** — 通用能力，文本场景也能用（事件流漏报时兜底），<10ms，零风险
2. **屏幕指纹 + 决策缓存** — 「同屏同目标复用决策」，省云端调用，零风险
3. **条件计划执行器（`scr run`）** — **最大提速杠杆**（10 步流程 20-50s → 2-4s），纯本地逻辑
4. **动作原语库** — 游戏/复杂手势的地基，工具性无风险
5. **MediaProjection 帧源 + 视觉决策** — 游戏路径，**需主人确认合规边界后再做**

## 7.5 动态视觉场景实测（v1.2.122，emulator-5554）

回答主人的问题：「面对动态视觉场景，方案可不可行、能否准确响应」——
**可以，以下为实测而非推断。**

| 场景 | 操作 | 结果 | 判断 |
|---|---|---|---|
| **A 静态** | 桌面静置采 6 次 | **误报 0/6**，ratio=0.0 | ✅ 不误报 |
| **B 动态** | 开关通知栏 12 次 | **检出 10/12**，ratio 0.06~0.95 | ✅ 高检出 |
| **C 单次交互** | 点设置齿轮 | changed=true，ratio=0.0325 | ✅ 单次交互可捕获 |
| **C 热点定位** | 同上 | 热点 `nx 0.62/0.88, ny 0.12` | ✅ **正指向齿轮位置** |
| **D framewait** | 变化后多久发现 | **0.25s** | ✅ 远快于固定 sleep |
| **帧成本** | 截图+比对 | min 44ms / p50 ~55ms / max 92ms | 含截图 IPC |

### 关键结论

1. **可行**：动态场景下，「画面变了没」能被稳定、准确地判断（0 误报、83% 检出）；
2. **能定位**：热点区域**指向真实变化位置**（不只是「变了」）——这是它作为
   **验证器**（我点的位置生效了吗）和**方向信号**（什么在动，下一步该往哪）的基础；
3. **余量充足**：p50 55ms，对比云端 1-3s 往返，**帧差可以高频调用**（做实时监控也够）；
4. **两处未命中说明边界**：通知栏连续开关时，若两帧恰好处于相同过渡态
   （都在全开或都在全关），比对不出差异 —— 持续动画场景需配合「连续两帧无变化
   才算稳定」的判据（已在 framewait 设计里）。

### 下一步（按这个数据排优先级）

帧差既已可用，接下来验证「**动态场景下能否做出正确决策**」：
- 接一条云端视觉路径（截帧 → 多模态模型 → 出动作），用热点区域做后验验证；
- 在游戏/视频类 Canvas 界面实测「发现变化 → 决策 → 执行 → 帧差验证」闭环。
