## 叙事结构（骨架给你，分镜你自己设计）

**核心洞察：短视频要赢在前 3 秒。** 不要用 logo 动画开场，那是浪费。

建议的叙事弧（你可以改，但要保持这个张力结构）：

1. **钩子（0~4s）**：先制造「不可能」的认知。屏幕上打出「在 Android 上跑完整 Node Agent 引擎」，
   然后**数秒内**直接切到冷启动实拍 + 倒数计时。让观众亲眼看到 3 秒。
2. **它凭什么快（4~14s）**：这里是全片的技术心脏。用**代码画的对比动效**讲清「没有中间层」：
   - Termux 路线：一条长长的链（Perl → apt → env → Node），逐节点亮起，总耗时「分钟级」
   - proot 路线：内核 → proot → glibc → 发行版 → Node，同样长链，「十几秒，部分设备起不来」
   - **DSH Mobile**：一条**直线**，一个箭头直达 Node，标「3.4 s」
   - 视觉上要让「长链」与「直线」形成强烈对比。这是全片最该记住的一帧。
3. **它凭什么值得换（14~30s）**：这里做**对比**，但要打得克制、打得诚实。

   **先说清一个前提**：与同类「bionic 直跑」型移植版（guzhou079、woaiys3 等）相比，
   **功能能力基本相同** —— 都是官方 dsh 引擎。所以**不要**做「我们有 XX、他们没有」式
   的功能勾选表，那既不准也显得心虚。

   真正站得住的对比只有两类：

   **(a) 架构路线对比图**（可验证，推荐做）

   画一张「从应用到 Node 引擎之间隔了几层」的示意图：

   ```
   proot + Ubuntu   [内核] → [proot 用户态翻译] → [glibc] → [完整发行版] → [Node]
   冻结快照         [内核] → [解压 rootfs] → [路径重定位] → [Node]
   bionic 直跑      [内核] → [Node]                      ← 本作与少数同类在这条线上
   ```

   视觉上让前两条的「链条」明显更长。这是**结构性事实**，不是营销话术。
   注意：**bionic 直跑这条线不止我们一家**，图里要如实标示这一点（画三个并排的点或
   标注「本作 / 另有两款同类」），否则一经核对就失信。

   **(b) 体积对比 —— 必须画三个口径，绝不能混**

   这是全片**最容易翻车**的地方。我们的「简单包」24 MB 看着小，但首次启动还要
   再下 128 MB 运行时，**首次总下载约 152 MB，与完整包 149 MB 几乎相同**。
   只画「安装包体积」会构成误导。所以必须分三组：

   **口径一 · 安装包体积**（用户点下载时看到的数字）

   ```
   dphmoblie    ████████████████████████████████ 392 MB
   DSHA         ██████████████████████ 279 MB
   woaiys3      ████████████ 155 MB
   本作(完整包)  ████████████ 149 MB
   guzhou079    █████████ 118 MB
   DSHBox       █████████ 112 MB
   dsh-phone-root ███ 41 MB (+ 需另装 Termux)
   本作(简单包)  ██ 24 MB (+ 首启下载 128 MB)
   ```

   **口径二 · 首次可用总下载量**（用户真正付出的流量）

   ```
   dphmoblie    ███████████████████████████████ 392 MB
   DSHA         ██████████████████████ 279 MB
   woaiys3      ████████████ 155 MB
   本作(任一种包) ████████████ ≈150 MB
   guzhou079    █████████ 118 MB
   DSHBox       █████████ 112 MB
   dsh-phone-root ███ 41 MB + Termux App
   ```

   **口径三 · 解压后磁盘占用**

   ```
   dphmoblie    ████████████████████████████████████ 1297 MB  ← 完整 Ubuntu
   woaiys3      ███████████████ 462 MB
   DSHA         ██████████████ 440 MB
   本作         █████████████ 404 MB
   guzhou079    ████████████ 370 MB
   ```

   **诚实要求（逐条遵守）**：
   - 三个口径**必须都画**。只画口径一（24 MB）是误导，只画口径三（404 MB）是自曝其短
   - 口径一里必须显示简单包那 24 MB **旁边标注「+ 首启下载 128 MB」**，
     不许只写 24 MB 让它显得最小
   - **保留所有比我们小的柱子**（DSHBox 112、guzhou079 118、dsh-phone-root 41），
     不得暗示「体积最小」
   - 架构图里**如实标注「bionic 直跑不止我们一家」**（另有两款同类）
   - 口径三里我们排第 4，**照实画**。真优势是「对比 proot 类体积小一半以上」，
     不是「最小」

   **可以打的点**（都真实）：
   - 与 proot/发行版路线相比，安装包小一半以上（149 vs 279/392）
   - 解压占用只有 dphmoblie 的三分之一（404 vs 1297 MB）
   - **完整包不需要任何二次下载**，装完即用、可离线启动

   **(c) 原生外壳完整度 —— 这是本作真正的优势，建议做成全片高潮**

   用户反馈「用了十几款，就这款最好」。实测下来这不是错觉：各家都能把 dsh 引擎
   跑起来（那是上游的功劳），但**帮引擎干活的这层原生外壳，厚度差一个量级**。

   **最有力的一组数据**（同为 bionic 直跑路线，可比性最强）：

   ```
   原生代码体量（dex 大小）
   guzhou079    ▏0.7 MB
   woaiys3      ▏0.6 MB
   本作         ████████████████ 9.3 MB      ← 15 倍
   ```

   **自有原生库**：
   - 本作：`libdsh_pty_exec.so`（自写 PTY 助手）+ `libdshpty.so` + `libtermux.so`
     + `libmlkit_google_ocr_pipeline.so`（自带 OCR）
   - guzhou079 / woaiys3：**一个自有 so 都没有**，纯 Java 外壳

   **能力实现覆盖**（dex 层实证，下界估计）：

   | 能力 | 本作 | 抽查竞品 |
   |---|---|---|
   | 无障碍服务 | ✅ | ✅（都有）|
   | 悬浮窗/桌宠 | ✅ | 部分 |
   | 自有 PTY（非空壳） | ✅ | 仅 1 家 |
   | 内置 SSH（ssh2） | ✅ | **无** |
   | 自带 OCR（MLKit） | ✅ | **无** |
   | 社区插件市场 | ✅ | 2 家 |
   | 扩展中心 21 项 | ✅ | 1 家 |
   | 局域网 WebUI | ✅ | 2 家 |
   | 数据导入导出 | ✅ | 3 家 |
   | **合计** | **10/10** | **3~5/10** |

   **怎么讲这段（关键）**：
   不要做成「我们功能更多」的勾选表 —— 那没说服力。要讲成**「为什么用户会觉得好用」**：

   > 引擎是上游给的，各家一样。
   > 差别在于引擎想干一件事时，有没有人为它在 Android 上铺好路。
   > 想开终端？有人写了 581 行 C 做真 PTY，有人只是塞了个一调用就抛错的空壳。
   > 想读屏幕？有人自己接了 OCR，有人只能拿到无障碍树（而很多 ROM 拿不到）。
   > 想连服务器？有人内置了 SSH 客户端，有人的 Agent 只能说「我做不到」。

   视觉上建议：把「同一个引擎，不同的外壳」做成对照 —— 左边是引擎的意图气泡，
   右边是本作 vs 竞品各自的响应（一个亮起、一个灰掉/报错）。这比柱子图更打动人。

   **诚实边界**：说「我们的实现覆盖 10 项，抽查的竞品覆盖 3~5 项」，
   **不要说「他们没这些功能」** —— 特征匹配是下界估计，没匹配到不等于没有。

   **(d) 功能厚度 —— 54 个核心模块，这是「好用」的实体**

   之前只讲 10 项大功能是不够的：代码里实际是 **102 个 Kotlin 文件 / 43185 行 /
   54 个核心模块**。这是「原生外壳厚 15 倍」的具体内容，建议挑 3~4 个最硬的讲：

   | 亮点 | 一句话讲清它解决什么 |
   |---|---|
   | **视觉三层兜底** | 无障碍树 → 视觉追踪 → 帧差验证。ColorOS/游戏拿不到节点树时，后两层顶上 |
   | **场景记忆** | 记住成功路径，同样场景直接走 —— 「越玩越聪明」 |
   | **快速决策层** | 把模糊判断压成「非黑即白的选择题」，减少模型往返 |
   | **zstd 多帧解压** | dsh 会话是 zstd 多帧格式，普通库解不了，自己写解析 |
   | **孤儿进程回收** | AI 起的进程没销毁会阻塞工作区，自动清理 |
   | **两阶段换装** | 换运行时被 OEM 杀进程时不留下半新半旧的坏状态 |

   视觉建议：把「54 个模块」做成**星系/网络图**——中心是引擎，周围 8 个域，
   每个域里散落模块节点，逐个点亮。比列文字更有体量感。

   **(e) 性能数据 —— 但要讲清口径**

   实测（Android 16 x86_64 模拟器 / 2.5 GB）：

   | 指标 | 值 |
   |---|---|
   | 冷启动（3 次） | 3.1 / 3.6 / 5.1 秒（中位 3.6） |
   | 稳态 PSS | **112 ~ 118 MB** |
   | App 进程 RSS | 272 MB |
   | node 引擎进程 | 154 MB |
   | 进程数 | 1 个 App 进程（引擎是子进程） |
   | 线程数 | 65 |

   **必须遵守的口径纪律**：
   - **PSS 与 RSS 不能混用**。安卓有四种内存口径，跨产品比较必须同口径，
     否则就是「自己 PSS 比别人 RSS」这种自欺
   - 模拟器数据要**明确标注「模拟器，非真机」**，不能拿它暗示真机表现
   - 真机冷启动 **3.4 秒**（一加 15T）是用户实测，这个可以理直气壮讲
   - 竞品的性能数据我们**没有同条件实测**，不许并列比较

   **(f) 我们的专属数字**（用数字滚动动效砸出来）   **绝对禁止**：不得出现「竞品启动要 X 秒」这类**未实测**的并列数据。
   我们只在自己的设备上测过自己的冷启动（3.4 秒 @ 一加 15T）。
   要做竞品启动对比，前提是同一设备、同一方法、各 3 次取中位并附原始数据 —— 没有就别画。
4. **可信度（28~36s）**：讲工程深度。14 个 Android 补丁、581 行 C 写的 PTY、
   两阶段提交换装、16 项回归探针。这一段要「冷静、硬核」，配色收一点，靠代码感的排版取胜。
5. **收尾（36~42s）**：回到品牌。`DeepSeek Harness. Now in your pocket.` +
   `No Root · No Termux · No PC` + 下载入口二维码或链接。

## 两个必须自己想清楚的设计难题

**难题一：3.4 秒怎么拍？**

冷启动真实录屏有 28 秒（含解压）。直接变速会显得仓促、也看不清。你的选择可能是：
变速 + 关键时刻定格放大、或干脆用代码重绘一个「压缩版启动时间线」（进度条 + 阶段标签 + 秒数跳动）。
两条路都行，但**必须让观众相信这是真实数据**，而不是随便打了一个数字。想清楚用什么视觉语言建立这种可信度。

**难题二：对比图怎么画才既有力又不失实？**

这是个真实的两难：我们是同类 bionic 路线里的一员，功能上拉不开差距；
但架构路线和体积确实有可验证的优势。

你的任务是**把「诚实」变成一种叙事力量**：在对比图里主动暴露「我们不是最小、也不是唯一」，
然后让观众觉得——「这家愿意说实话，那它说的其他话应该也可信」。

具体怎么处理，你自己想。但底线是：**任何一帧都不能因为想赢而失真。**
做对的对比图，比做夸张的对比图更能让人下单。

**难题三：技术深度怎么讲才不无聊？**

「14 个补丁」「581 行 C」「两阶段提交」这些是全片最有含量、也最容易让观众划走的部分。
你不能只是把文字打出来。考虑用：代码流水的视觉化、补丁逐个"命中"的动效、
或者把「两阶段提交」画成一个有明确状态机的示意图。**要让不懂技术的人觉得酷，让懂的人觉得对。**
